# 每用户个人空间 + 邀请码准入方案

> 目标：让 `qlib-lab` 从「单用户全局工具」过渡到「小圈子多租户」。
> 核心思路：**门禁（Cloudflare Zero Trust） + 应用内准入（邀请码） + 按用户隔离数据**。

## 1. 背景与问题

当前存在两个现实问题：

| 问题 | 现状 | 根源 |
|---|---|---|
| **自选股不一样** | 全局只有一套 `symbols`，所有人都看到同一批股票。 | UI/后端都没有「用户」概念，数据全局。 |
| **模拟交易（Alpaca Paper）安全** | 全局共用 `.env` 中的同一套 API 密钥，任何能访问网站的人都能用它下单、查账户。 | 无鉴权 + 无按用户隔离密钥。 |

把自选股汇总到一起只是应急做法，长久不可行。必须做「每个用户一个个人空间」。

## 2. 门禁 vs 应用内用户系统的关系

这两者是「外层门禁」和「内层多租户」的区别，不能互相替代。

| 对比项 | **Cloudflare Zero Trust（邮箱白名单/验证）** | **应用内用户系统（邀请码/权限）** |
|---|---|---|
| **作用层级** | 边缘（门禁）。请求到达应用前拦截。 | 应用内（多租户）。决定「这个人能看到什么、用什么数据」。 |
| **决定什么** | 「谁能访问这个网站」 | 「谁能用哪些功能、看到哪些数据」 |
| **自选股隔离** | 不能 | 能（必须在应用内实现） |
| **模拟交易密钥隔离** | 不能 | 能（必须在应用内实现） |
| **能否替代注册页** | 能（用 `Cf-Access-Authenticated-User-Email` 自动识别） | 不能替代门禁本身 |
| **能否让朋友自助邀请** | 不能（Cloudflare 白名单需手动添加） | 能（应用内邀请码） |

**核心认知：Zero Trust 解决「门」的问题，应用内用户系统解决「家」的问题。**

## 3. Cloudflare Zero Trust 配置思路

### 3.1 从「指定邮箱」改为「允许通过身份验证的任意邮箱」

目标：省去「注册表单」和「手动逐个加白名单」的麻烦，让朋友能走邮箱验证直接到达应用，再由应用内邀请码控制准入。

**操作入口：** [one.dash.cloudflare.com](https://one.dash.cloudflare.com/) > `Access` > `Applications` > 找到 `qlib-lab` 应用 > `Policies` 编辑 `Allow` 策略

| 改动前 | 改动后 |
|---|---|
| `Include: Emails`（列出具体邮箱） | `Include: Everyone`（所有通过身份验证的邮箱） |
| 需手动添加每个新朋友的邮箱 | 朋友只需通过邮箱 OTP 验证即可到达应用 |

### 3.2 登录方式

在 `Zero Trust` > `Settings` > `Authentication` 中确保至少启用：

- **推荐：** `One-time PIN`（邮箱验证码）—— 最适合小圈子，无需 OAuth 账号
- 可保留其他 IdP，但不是必需

### 3.3 测试与回滚

- **测试：** 用无痕窗口，用不在原白名单的邮箱走验证，确认能跳转到站点
- **回滚：** 若出问题，将 `Include` 改回 `Emails` 并恢复之前备份的邮箱列表即可

> **注意：** 放开成 `Everyone` 后，门禁只剩「能否通过邮箱验证」。必须配合应用内邀请码才能真正控制谁能用。

## 4. 应用内邀请码系统设计

要实现「朋友能自助推荐」，必须把准入从 Cloudflare 转移到应用内。

### 4.1 整体流程

1. **朋友点开链接** → 跳转到 Cloudflare Access，走邮箱 OTP 验证通过 → 到达 `qlib-lab`
2. **应用识别身份** → 读取 `Cf-Access-Authenticated-User-Email`，查找是否已存在应用内用户
3. **若不存在** → 强制跳转到「邀请码输入页」，要求输入邀请码
4. **邀请码校验通过** → 自动创建用户，标记邀请码已使用，跳转首页
5. **已存在用户** → 直接进入，按用户隔离的数据生效

### 4.2 邀请码规则

| 字段 | 建议值 | 说明 |
|---|---|---|
| **code** | 随机字符串（如 `INV-XXXX-XXXX`） | 唯一且不可猜测（建议用 `secrets.token_urlsafe`） |
| **created_by** | `user_id`（admin） | 谁生成的，便于审计 |
| **used_by** | `user_id` 或 `null` | 首次使用后填入，防止重复使用 |
| **max_uses** | `1`（推荐） | 一次性邀请码最安全。也可设为 `N` 但需额外限制 |
| **expires_at** | 建议 24-72 小时 | 防止长期泄露 |
| **used_at** | 时间戳 | 使用时间 |
| **created_at** | 时间戳 | 创建时间 |

### 4.3 权限控制

- **只有 `admin` 能生成邀请码**：在管理后台 `/admin/invites` 只有 `role == 'admin'` 可访问
- **生成可配额**：可选限制「最近 X 小时最多生成 Y 个」，防止误操作批量生成
- **一次性优先**：默认 `max_uses=1`，用过即失效
- **邀请码泄露风险**：如果发到群里被截获，任何人都能用。一次性 + 短有效期是最有效的降低方式

## 5. 数据模型设计（SQLite）

用最简的 SQLite 表即可满足需求。所有敏感字段都要加密存储。

| 表 | 字段（核心） | 用途 |
|---|---|---|
| **`users`** | `id`(PK), `email`(UNIQUE), `role`(`user\|admin`), `status`(`active\|pending`), `created_at`, `last_login_at` | 应用内用户身份。以邮箱为主键关联（来自 CF Header） |
| **`invites`** | `id`(PK), `code`(UNIQUE), `created_by`, `used_by`, `max_uses`, `used_count`, `expires_at`, `created_at`, `used_at` | 邀请码池。支持一次性/限次/过期 |
| **`user_watchlist`** | `id`(PK), `user_id`(FK), `market`(`cn\|us`), `symbol`, `added_at` | **每人自选股**。替换全局自选列表，首页只读当前用户的列表 |
| **`user_broker`** | `id`(PK), `user_id`(FK), `api_key_enc`, `secret_enc`, `base_url`, `updated_at` | 每人自带 Alpaca Paper 密钥（**加密存储**）。强制锁定 `https://paper-api.alpaca.markets` |
| **`user_positions`**（可选） | `user_id`(FK), `data_json` 或按文件隔离 `data/private/users/{user_id}/positions.json` | P2 本地账本也按用户隔离，避免互相可见 |
| **`audit_log`**（强烈建议） | `id`(PK), `user_id`, `action`, `ip`, `user_agent`, `detail_json`, `ts` | 审计敏感操作：登录、生成邀请码、下单、撤单、密钥变更等 |

### 5.1 密钥加密（核心）

- **主密钥：** 在 `.env` 新增 `QLIB_MASTER_KEY`，用 `cryptography.Fernet` 生成
- **加密：** 用户在「个人设置」填入 Key/Secret 时，用 Fernet 加密后写入 `user_broker`
- **解密：** 发起 Alpaca 请求时，根据当前用户解密，仅在内存中使用，用完即丢弃
- **掩码显示：** 前端只显示密钥前几位+后几位（如 `PKAB...XXXX`），绝不返回完整密钥
- **不打日志：** 请求体、日志、异常都不得包含明文密钥

## 6. 身份识别与信任边界

### 6.1 读取 CF Header

Cloudflare Access 验证通过后会添加：

- `Cf-Access-Authenticated-User-Email`（最常用）
- `Cf-Access-Jwt-Assertion`（可选，用于更严格校验）

### 6.2 信任原则（极重要）

| 原则 | 说明 |
|---|---|
| **仅信任 Tunnel 流量** | **只在请求来自 Cloudflare Tunnel（或可信代理）时才读取该 Header**。如果应用直接暴露公网且未走 Tunnel，绝对不要信任这个 Header（Header 可伪造）。 |
| **以邮箱为身份** | 用 `email` 作为应用内用户的唯一标识，自动建用户而非让用户手动注册。 |
| **自动建用户** | 首次通过验证且邀请码校验通过后，自动创建 `users` 记录并初始化空的 `user_watchlist`。 |
| **会话管理** | 建议用 `Flask-Login` 管理应用内会话。CF 只做「门禁」，应用仍需自己的登录态。 |

## 7. 数据隔离改造清单

| 模块 | 改造方式 | 说明 |
|---|---|---|
| **首页自选股** | 改为按 `user_id` 查询 `user_watchlist` | 移除全局自选，改成「我的自选」。新增/移除走用户维度接口。 |
| **qflib/因子/信号** | 按当前用户的自选股范围处理 | 避免加载全局列表，且天然隔离不同用户的关注范围。 |
| **模拟交易（Broker）** | 强制用当前用户的密钥 | `/api/broker/*` 全部校验登录状态 + 用户是否配置密钥。没配密钥就禁用下单并提示去「个人设置」配置。**彻底移除对全局 `.env` 密钥的兜底**。 |
| **P2 持仓账本** | 按用户隔离存储 | 建议改为 `data/private/users/{user_id}/positions.json`，或在文件内按 `user_id` 分组。确保 A 看不到 B 的本地账本。 |
| **管理后台** | 限制 `admin` | 邀请码管理、审计日志等仅 `admin` 可访问。 |
| **接口权限** | 全量加 `@login_required` | 所带敏感数据的 API 都要校验登录态，且只能操作当前用户的数据。 |

## 8. 实施顺序（渐进式）

按「先关门、后分家」的思路，循序渐进最不容易把现有功能搞崩。

| 步骤 | 内容 | 优先级 | 说明 |
|---|---|---|---|
| **1. 安全兜底** | 收紧访问 | P0 | 若已用 Cloudflare Tunnel 暴露，先配好 Zero Trust（可先用白名单过渡），再逐步放开。 |
| **2. CF 门禁改造** | 从白名单改为 `Everyone` | P0 | 按上文操作，先小范围测试。改动前备份白名单。 |
| **3. 应用内用户基础** | 加 `Flask-Login` + `users` 表 | P0 | 读取 `Cf-Access-Authenticated-User-Email`，实现自动建用户。先不做邀请码也能跑通身份识别。 |
| **4. 邀请码系统** | `invites` 表 + 生成/校验 + 管理后台 | P0 | 这是解决「朋友能推荐」的核心。只有 `admin` 能生成，一次性 + 过期。 |
| **5. 自选股隔离** | `user_watchlist` 替换全局自选 | **P0（最关键）** | 解决「每个人关注的股票不一样」这个痛点。做完后体验立马上升。 |
| **6. 模拟交易 BYOK** | `user_broker` 加密存储 + 按用户取密钥 | P1 | 配合门禁和邀请码，真正杜绝共用全局密钥。没配密钥就禁用下单。 |
| **7. 账本隔离** | P2 按用户隔离 | P1 | 避免隐私泄露。 |
| **8. 审计与收尾** | `audit_log` + 日志脱敏 + 清理全局密钥兜底 | P2 | 收尾优化，跑稳后再做。 |

## 9. 安全要点总结

| 要点 | 建议 |
|---|---|
| **密钥托管风险** | 不要代管他人的密钥。优先走 **BYOK（自带密钥）** 而不是「服务器统一托管」。 |
| **加密存储** | 密钥必须用 `QLIB_MASTER_KEY` 加密后存储，且主密钥只存在 `.env`，绝不可提交 git。 |
| **只信任 CF Header** | 只在可信来源（Cloudflare Tunnel）时读取 `Cf-Access-Authenticated-User-Email`。 |
| **邀请码控制** | 生成权限只给 `admin`，推荐一次性+短有效期。 |
| **权限最小化** | `@login_required` 全覆盖，接口只操作当前用户的数据。 |
| **日志脱敏** | 禁止在日志里打印密钥、完整邀请码等敏感信息。 |
| **审计可追溯** | 记录下单、撤单、密钥变更、邀请码生成等敏感操作。 |
| **回滚预案** | 保留 Cloudflare 白名单备份，随时可恢复门禁。 |

## 10. 注意事项

- **完全撒手不管不现实：** Cloudflare 白名单这一步得手动操作，新加朋友需要你点一下。但用邀请码后，**朋友能自助推荐别人**，你就不用再为每个新朋友跑去 Cloudflare 后台加邮箱了。
- **光有门禁解决不了隔离：** Cloudflare 只管「准不准进」，必须在应用内做自选股、模拟交易、账本隔离。
- **先改应用再放开规模：** 建议先用邀请码系统本地跑通，再把 Cloudflare 改成 `Everyone`，最后再小范围发邀请码测试全流程。
- **暂时只做小圈子：** 如果只是十来个人试用，用以上方案已经足够平衡「体验」「安全」「实现复杂度」。
- **邀请码生成权限最关键：** 只要把「生成邀请码」的权限牢牢握在你自己的 `admin` 账号上，就能既满足「朋友能带人」的需求，又不会让网站彻底失控。

## 11. 实施状态（2026-11-03）

### P0 已完成

- `Flask-Login` + `users` 表；身份来自 `Cf-Access-Authenticated-User-Email`。
- `QLIB_ADMIN_EMAIL` 首次登录自动建 admin，并继承现有全局股票池为自选。
- `invites` 表 + `/admin/invites` 管理页；一次性、默认 72 小时、24h 配额。
- `user_watchlist` 隔离：侧栏「我的自选」、全量池添加/移出、新增股票自动进发起人自选。
- 未准入邮箱自动进入 `/invite` 输入邀请码。
- 会话密钥自动生成到 `data/private/session_secret`；用户库在 `data/private/qlib_lab.db`。

### P0 的安全取舍

- 模拟交易（`/api/broker/*`）在 P1 BYOK 前**仅 admin**，避免共用 `.env` 里的 Alpaca 密钥。
- 持仓账本（`/api/positions*`）在 P1 按用户隔离前**仅 admin**；非管理员首页显示 P1 提示。
- 持仓底层仍是全局 `data/private/positions.json`，这是 P1 的主要收尾项。
